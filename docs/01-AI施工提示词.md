## 三、P2 · 业务核心：StockCommand 与库存执行力

```
【上下文】四张表已就绪。现在要实现整个应用唯一的数据修改入口 —— 这是设计上的关键点：语音、手动、将来的扫码，都必须收敛到同一条代码路径。

【任务】实现 src/services/stockService.ts。

1. 定义类型：
   StockCommand = { action: 'IN' | 'OUT' | 'SET'; productHint: string; colorHint?: string; sizeTenth?: number; amount: number }
2. 定义返回类型 ApplyResult，必须是可辨识联合：
   - { kind: 'ok'; sku: Sku; product: Product; delta: number }
   - { kind: 'ambiguous'; candidates: SkuWithProduct[] }   // 匹配到多个 SKU
   - { kind: 'notFound' }
   - { kind: 'insufficient'; current: number }             // 出库数量大于现存
   - { kind: 'needSize' }                                  // 没听出码数
3. applyCommand(cmd: StockCommand, source: 'manual' | 'voice'): Promise<ApplyResult>
   —— 纯计算 + 校验，**不弹 UI、不写库**。它只返回"将会发生什么"。
4. confirmApply(result: ApplyResult, skuId: number): Promise<void>
   —— 真正写库。在同一个事务里：更新 sku.stock + 插入 stock_log。

【关键要求】
- applyCommand 和 confirmApply 必须分离。前者用于"生成预览给确认卡看"，后者是用户点头后才执行。不要合并。
- 匹配 SKU 时，productHint 要同时匹配 product.name 和 product.searchKey（searchKey 里存着别名和拼音）。用 LIKE 而非等值。
- OUT 且 amount > stock 时必须返回 insufficient，绝不允许库存变负数。

【验收标准】
- 我手动新增一款鞋的两个 SKU，分别对它们执行 IN 5 / OUT 2 / SET 10，每次结果正确。
- 出库超过现存时被拦截，库存没有变成负数。
- 每次成功后 stock_log 都多一条记录，source 字段正确。
```

## 五、P4 · 语音：录音 → 识别 → 解析 → 确认

```
【上下文】手动录入已经好用。现在加语音。请务必先读懂 src/services/stockService.ts 的 StockCommand，语音链路的终点就是产出这个对象。

【任务】
1. 集成 @capgo/capacitor-audio-recorder 8.x（注意主版本必须与 Capacitor 8 一致）：按住录音、松手停止，拿到音频文件。
2. src/services/asr.ts：把音频文件读出 base64，POST 到百度短语音识别 REST API。凭证从 src/config/asr.ts 读取，**不要把凭证硬编码提交**，用 import.meta.env 的环境变量 + 本地 .env.local。
3. src/services/nlu.ts：**本地纯规则解析**，把一句中文文本解析成 StockCommand。必须支持：
   - 动作词：入库/进货/加了/到了  → IN；卖出/出货/卖了/少了 → OUT；盘点/改成/设为 → SET
   - 数量：支持阿拉伯数字和中文数字（三双、五件、十双）
   - 码数：识别「42码 / 42.5码 / 四十二码」，统一转成 sizeTenth
   - 颜色：白/黑/米/卡其/藏青 等常见色
   - 款名：剩下的部分
   - 解析不出必填项时，返回 { kind: 'needSize' } 之类的明确原因，不要瞎猜
4. src/views/VoiceView.vue：录音按钮 → 显示识别出的原始文本（便于纠错）→ 显示解析出的 StockCommand → **确认卡**（明确显示"将 Nike AF1 白 42码 库存 -1 → 剩余 4"）→ 用户点确认才 confirmApply。

【关键要求】
- 原始识别文本必须显示给用户看，不能只显示解析结果。用户看到文本错了会自己纠正说法。
- 确认卡不允许跳过，也不允许有"总是执行"的默认勾选。
- 解析逻辑要写单元测试（vitest），至少覆盖上面每一类说法。

【验收标准】
- 我说「空军一号白色的42码卖了一双」，能走到正确的确认卡。
- 我说一句完全无关的话，app 给出明确的"没听懂"，而不是乱改数据。
- npm run test 全绿。
```

## 七、给 AI 的持续反例清单（项目特有的坑）

在提示词末尾追加这一段，能挡住大部分返工：

```
【本项目已知坑，不要犯】
- 不要用 localStorage / sessionStorage 存业务数据：WebView 存储会被系统清掉，必须走 SQLite。
- 不要用 double / float 表示金额或鞋码，一律 int（金额存「分」，鞋码存「十分之一码」）。
- 不要给语音链路加"自动执行"开关或超时自动确认。改错一次库存要人工翻流水，代价远高于多点一下。
- 不要在Vue 组件里直接写 SQL。SQL 只允许出现在 src/db/repositories/ 下。
- 不要为了所谓的"更聪明"引入 Agent / LLM 自主循环。这个场景是单步指令执行，引入只会增加延迟和不确定性。
- 不要引入后端服务。这个 app 是纯离线的，加服务端会破坏它最大的优势。
```
